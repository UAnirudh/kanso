Kanso

A Next.js application in which every person generates their own interface — layout, components, theme — on top of one shared project workspace. Data and permissions stay shared; presentation is per-user, schema-validated and versioned.

This Pages site hosts the documentation, not the running app.

Kanso needs a Node.js server, API routes and a SQLite database. GitHub Pages is a static file host with no server runtime and no database, so the application cannot be served from here. To use it, run it locally or deploy it to a host with a persistent disk.

Run it locally

git clone https://github.com/UAnirudh/kanso.git
cd kanso
npm install
npm run db:migrate
npm run dev   # http://localhost:3000

No external services are required. The interface assistant works without an API key using a clearly labelled deterministic planner; set GROQ_API_KEY (and optionally GROQ_MODEL) to use a Groq model. Node.js 20.9+.

How it works

  1. The interface is a typed JSON document: theme, accent, density, navigation, pages and components with props and a 12-column layout.
  2. A catalogue of ten components declares each one's prop schema and defaults, span bounds, allowed data bindings and accessibility contract.
  3. Changes arrive as one of fourteen typed operations — from the assistant or the visual editor — and are validated, normalised and packed without overlap before they are saved.
  4. Documents are stored per (application, user) with append-only revisions, so undo and restore are themselves reversible, and no one can change another person's interface.
  5. The model never emits code. It is called with JSON object mode, its output is checked against Zod schemas with one repair round, and nothing is applied until the user previews and confirms it.

Deployment

The repository ships a Dockerfile and a Render Blueprint (render.yaml) with a 1 GB disk mounted at /var/data for DATABASE_PATH. Render's Free plan cannot attach a disk; the cheapest disk-backed configuration is roughly $7.25/month, or about $3.84/month elsewhere.

Deploy to any host that runs next start and can mount a persistent disk — Fly.io, Render, Railway or a VM. Serverless platforms such as Vercel and static hosts such as GitHub Pages are not suitable as-is, because the SQLite driver writes to local disk and the app has server-side routes.

Set GROQ_API_KEY as a server-side secret only. It is read inside server modules and is never exposed to the browser.

Status

  • Type-check and production build pass; 32 unit tests and 2 Playwright acceptance tests pass.
  • The Groq integration is implemented and its error path is verified against the live API; a successful model completion is unverified without a funded key.
  • Application generation is template-constrained by design, not arbitrary software generation. Real-time collaboration, SSO and email invitations are not implemented.
